# InsightFlow Product Brief

> 文档状态：Day 1 产品定义  
> 目标读者：产品评审者、设计与研发协作者、作品集面试官  
> 指标说明：本文中的数值均为 MVP 验证目标，不代表实际测试结果。

## 1. Product Overview

### 产品名称

**InsightFlow — AI 用户研究与产品分析 Agent**

### 一句话定位

面向产品经理和用户研究人员的 AI 用户洞察平台，通过大语言模型批量分析用户评论、问卷和客服记录，将非结构化反馈转化为可追溯的用户痛点、需求优先级、产品机会与 PRD 草稿。

### 产品背景

产品经理在版本迭代和 Roadmap 规划中，需要持续处理来自 App Store、问卷、客服与社交媒体的大量用户反馈。传统流程依赖人工阅读、标注、聚类和总结：数据量上升时耗时显著增加，而且不同分析者可能对同一批反馈得出不同结论。

InsightFlow 将原本的“产品经理人工逐条阅读”改造为：

> AI 批量分析 + 产品经理审核关键洞察

第一版聚焦三个问题：

1. 大量用户反馈难以快速整理；
2. 高频痛点难以从非结构化文本中稳定识别；
3. 用户声音难以转化为有证据支持、可继续评估的产品需求。

## 2. Problem Statement

### Problem 01：人工阅读成本高

**现象：** 产品经理需要逐条浏览大量反馈。以 1,000 条评论、每条阅读与初步判断 20 秒估算，仅阅读就需要约 5.5 小时，尚未包含标注、聚类和报告时间。

**原因：** 原始反馈分散、格式不统一，传统工具主要承担存储和表格计算，无法理解语义。

**结果：** 分析周期长，版本决策容易依赖少量近期反馈或个人印象。

**待验证假设：** AI 能否把数小时的整理工作压缩为数分钟的自动分析，再由产品经理进行集中复核。该表述是产品假设，不是已实现的效率成果。

### Problem 02：反馈高度非结构化

一条反馈可能同时包含多个主题、事实和情绪。例如：“最近越来越不好用了，以前保存的东西根本搜不到，有时还会直接卡死。”其中至少包含搜索、历史内容检索、稳定性和负面情绪。

关键词统计难以识别这些语义关系。InsightFlow 的核心价值之一，是把自然语言转换成带来源引用的结构化数据，并允许一条反馈归属多个主题。

### Problem 03：用户声音不等于产品需求

用户提出“增加按年份搜索按钮”，并不意味着指定功能就是唯一答案。其底层需求可能是“快速定位历史内容”。如果直接执行用户给出的方案，团队可能跳过问题理解和方案探索。

InsightFlow 采用以下推导链路：

> Feedback → Pain Point → User Need → Product Opportunity → Requirement

每一步都必须能够回溯至原始反馈，产品经理仍需结合战略、成本、商业价值和技术约束做最终决策。

## 3. Target User

### 核心用户

**拥有 1–5 年经验的互联网产品经理或 AI 产品经理。**

他们通常：

- 每周需要查看和整理用户反馈；
- 负责产品版本迭代、需求分析和优先级讨论；
- 熟悉 Excel、飞书或多维表格；
- 已经尝试使用 ChatGPT 等 AI 工具，但未必具备编程能力；
- 在反馈量增加时，分析效率和结论一致性明显下降。

### 次级用户

用户研究员、运营经理和 Customer Success 也有类似需求，但 MVP 的工作流、信息架构和评价标准优先围绕产品经理设计。

### 暂不服务

- 只需要社交舆情监控的市场团队；
- 需要企业级实时数据管道、复杂权限和多人协作的大型组织；
- 希望 AI 自动决定 Roadmap、无需人工审核的团队。

## 4. Persona

### 张景，28 岁，SaaS 产品经理

| 属性 | 描述 |
| --- | --- |
| 工作经验 | 3 年 |
| 团队组成 | 1 PM、1 Designer、6 Developers |
| 主要职责 | 用户反馈、需求与竞品分析、PRD、数据分析、Sprint 规划 |
| 反馈来源 | App Store、客服、企业微信群、问卷 |
| 反馈规模 | 每周约 200–500 条 |

**当前工作流**

> 导出反馈 → 汇总至 Excel → 人工阅读 → 添加标签 → 统计数量 → 总结高频问题 → 讨论优先级 → 编写 PRD

**核心痛点**

> “不是没有用户反馈，而是反馈太多，不知道哪些真正值得做。”

**目标**

在 10–30 分钟内了解一批反馈中最重要的 5–10 个问题，快速查看证据，再进行人工判断。

**对 AI 的顾虑**

- AI 是否会错误分类或遗漏少数但严重的问题？
- 洞察是真实归纳，还是脱离原文的概括？
- 优先级分数由什么因素构成，为什么某项是高优先级？
- 是否能查看支持某项洞察的原始反馈？
- 当分析失败或信心不足时，系统是否明确提示？

因此，**可追溯性（Traceability）** 是核心产品要求：任何 AI 洞察都应回答“哪些原始反馈支持这个结论？”

## 5. Jobs To Be Done

### JTBD 01：理解（Understand）

当我收到大量用户反馈时，我希望快速了解用户主要在讨论什么，以便识别当前产品最严重的问题。

### JTBD 02：排序（Prioritize）

当我规划下一个版本的 Roadmap 时，我希望比较不同需求的出现频率、严重程度和影响范围，以便形成可解释的优先级建议。

### JTBD 03：行动（Act）

当我发现一个高价值用户问题时，我希望查看相关证据，并将痛点推导为可编辑的产品机会和需求草稿，以便进入 PRD 与研发流程。

三个 JTBD 构成产品的信息架构主线：

> Understand → Prioritize → Act

## 6. Core Scenarios

### Scenario A：版本发布后的反馈分析

产品发布 Version 3.0 后，PM 导出 1,000 条用户评论并上传。系统完成字段映射、数据预览和批量分析，展示负面主题及反馈数量，例如搜索体验、稳定性、价格、登录和导出。

PM 打开“搜索体验”后，可查看子痛点、典型反馈和全部关联证据。例如，186 条搜索相关反馈中有 107 条涉及历史内容无法检索。PM 据此创建“历史搜索优化”产品机会。

**成功条件：** PM 能从汇总洞察下钻到原文，并能纠正错误归类。

### Scenario B：Roadmap 规划

PM 需要在 Dark Mode、搜索优化和批量导出之间确定优先顺序。InsightFlow 根据反馈证据提供频率、严重程度、影响范围及透明的建议分数。

| Requirement | Frequency | Severity | Impact | Example Score |
| --- | ---: | --- | --- | ---: |
| 搜索优化 | 186 | High | High | 91 |
| 批量导出 | 83 | Medium | Medium | 67 |
| Dark Mode | 59 | Low | Medium | 47 |

分数用于比较，不代表系统自动决定 Roadmap。PM 需要结合战略契合度、商业价值、开发成本和风险做最终判断。

**成功条件：** 每个评分维度都有定义和证据，PM 可以修改参数或否决建议。

### Scenario C：生成需求方案

PM 从“搜索体验”进入痛点详情，查看：

- **Evidence：** 186 条相关反馈及代表性原文；
- **Pain Point：** 用户无法快速找到历史内容；
- **User Need：** 快速定位过去创建或收藏的信息；
- **Product Opportunity：** 改善历史信息检索能力。

PM 选择生成 PRD 草稿，系统基于已确认的洞察生成问题背景、目标用户、需求说明、成功指标和证据引用。草稿必须由 PM 编辑和确认后才能进入后续流程。

**成功条件：** PRD 中的事实性结论能够回溯至已确认证据；推测内容被明确标注。

## 7. Value Proposition

### 对产品经理

- **更快理解：** 将逐条阅读转化为主题、痛点与代表性证据的分层浏览；
- **更有依据地排序：** 用统一维度比较需求，并保留人工决策权；
- **更顺畅地行动：** 从已验证洞察生成可编辑需求草稿，减少重复整理；
- **更可信地使用 AI：** 所有关键洞察都可回溯、可纠正、可拒绝。

### 差异化价值

InsightFlow 不只是摘要器或词频面板。它围绕产品决策构建从原始证据到需求草稿的完整链路，同时把 AI 定位为可审核的分析助手。

## 8. MVP Scope

MVP 只验证一条完整闭环：

> Upload → Analyze → Insight → Decision

### P0：MVP 范围内

| 能力 | MVP 目的 |
| --- | --- |
| 创建项目 | 隔离不同产品或批次的分析上下文 |
| CSV / XLSX 上传 | 使用 PM 已有的导出数据，不依赖外部集成 |
| 字段映射与数据预览 | 在分析前确认内容、时间等关键字段 |
| AI 多标签分类与情绪分析 | 将反馈转为基础结构化数据 |
| Feedback 聚类与痛点识别 | 形成主题、子痛点和频次统计 |
| Requirement 提取 | 从痛点推导用户需求和候选需求 |
| Priority Score | 提供透明、可解释的排序参考 |
| 洞察 Dashboard | 展示主题、趋势、情绪和重点问题 |
| 原始 Evidence 查看 | 支持洞察到反馈的双向追溯 |
| Product Opportunity | 将已确认痛点转化为产品机会 |
| PRD Generator | 基于已确认内容生成可编辑草稿 |
| 批次失败与重试 | 单条失败不阻断整批分析 |

### Non-MVP：明确不做

- App Store API 与自动抓取评论；
- 实时分析；
- 多人协作、复杂权限与审批；
- Jira、飞书和 Slack 集成；
- AI 自动发布 PRD 或自动修改 Roadmap；
- 覆盖图片、音频、视频等多模态反馈。

## 9. Product Principles

1. **Decision Support, not Decision Making**  
   AI 提供证据、结构和建议，不替代 PM 做产品决策。

2. **Evidence First**  
   任何痛点、需求和优先级建议都必须能下钻至支持它的原始反馈。

3. **Human in the Loop**  
   用户可以接受、编辑、合并、拆分或拒绝 AI 输出，修正不会被隐藏。

4. **Uncertainty Is Visible**  
   当证据不足、分类存在歧义或模型处理失败时，系统应明确呈现不确定性。

5. **Structured, but Reversible**  
   AI 将文本结构化，但必须保留原始输入和推导关系，避免结构化过程丢失语境。

6. **Partial Failure over Batch Failure**  
   单条数据失败不应导致整个批次失败。系统应报告成功/失败数量并允许重试。

### 非功能要求

- **Explainability：** AI 洞察必须提供原始 Feedback Evidence；优先级分数需要说明组成维度。
- **Reliability：** 结构化输出需通过 Schema Validation；无效输出应重试或进入失败队列。
- **Privacy：** MVP 不使用用户上传数据训练模型；若调用第三方 LLM API，必须在上传前明确披露数据处理路径。
- **Error Handling：** 例如 1,000 条中 998 条成功、2 条失败时，应保留成功结果并允许单独重试失败项。

## 10. Success Metrics

### North Star Metric：Insight Acceptance Rate

PM 查看 AI 洞察后，认为洞察有效并选择保留的比例。

```text
Insight Acceptance Rate = Accepted AI Insights / Reviewed AI Insights
```

分母采用“已被 PM 查看并完成判断的洞察”，避免把尚未审核的洞察误判为无效。系统应同时记录编辑后接受、直接接受和拒绝，以便进一步理解输出质量。

### MVP 目标

| Metric | 定义 | MVP Target |
| --- | --- | ---: |
| Insight Acceptance Rate | 被直接接受或编辑后接受的洞察 / 已审核洞察 | ≥ 80% |
| 1,000 条反馈处理成功率 | 成功产生合法结构化结果的反馈 / 有效输入反馈 | ≥ 95% |
| Insight 可追溯率 | 至少关联一条有效原始证据的洞察 / 全部生成洞察 | 100% |
| 人工分析耗时变化 | 同一数据集使用与不使用产品的任务时间差异 | 记录基线，验证是否显著下降 |
| 核心任务完成率 | 用户能完成上传、理解、下钻和导出草稿的测试任务比例 | ≥ 80% |

上述数据均为验证目标。只有在完成统一数据集、人工金标和可重复用户测试后，才记录为 Actual Result。

## 11. AI Metrics

### 1. Feedback Classification Quality

衡量 AI 是否将反馈归入正确主题。由于一条反馈可以包含多个主题，不仅记录简单 Accuracy，还应优先使用多标签 Precision、Recall 和 F1，并在作品集摘要中报告人工抽检准确率。

**MVP Target：** 人工抽检分类准确率 ≥ 85%；同时保留 Precision、Recall 与 F1 作为诊断指标。

### 2. Requirement Extraction Accuracy

由人工评审 AI 是否基于原始反馈正确表达用户问题和底层需要，避免把用户提出的具体方案直接当成真实需求。

**建议评审维度：** 证据一致性、问题表述准确性、需要与方案的区分、是否包含无依据内容。

**MVP Target：** 人工评审通过率 ≥ 80%。

### 3. Hallucination Rate

AI 洞察或需求中，包含无法由关联原始反馈支持的事实性陈述的比例。

```text
Hallucination Rate = Unsupported Factual Claims / Reviewed Factual Claims
```

**MVP Target：** < 5%；长期目标接近 0%。

### 评估前提

- 使用包含单主题、多主题、反讽、模糊表达和少数严重问题的代表性测试集；
- 建立人工标注规范，并处理评审者意见不一致；
- 将提示词、模型版本、参数和数据集版本纳入评估记录；
- 单独检查“高频但低影响”和“低频但高严重度”两类边界案例。

## 12. Risks & Assumptions

| 类型 | 风险或假设 | 验证 / 缓解方式 |
| --- | --- | --- |
| 假设 | PM 愿意上传现有 CSV/XLSX，而不是要求系统自动拉取数据 | 原型测试上传与字段映射流程 |
| 假设 | PM 愿意审核 AI 洞察，而不是期望完全自动化 | 观察审核完成率与单条审核时间 |
| AI 风险 | 分类体系不稳定，同义主题被拆散或不同主题被错误合并 | 支持合并、拆分、编辑和批量复核；建立固定评估集 |
| AI 风险 | 高频问题掩盖低频但严重的安全或数据丢失问题 | 将严重度与频率分离，设置严重问题检测与人工复核入口 |
| AI 风险 | 需求提取脱离证据、生成不存在的问题 | 强制证据引用，计算 Hallucination Rate，禁止无来源事实进入已确认洞察 |
| 决策风险 | Priority Score 营造“客观正确”的错觉 | 公开公式和权重，允许修改，明确不纳入战略与开发成本时的局限 |
| 隐私风险 | 反馈可能含姓名、联系方式或企业敏感信息 | 上传前提示、最小化留存、支持脱敏，并披露第三方 API 路径 |
| 体验风险 | 大批量处理耗时或局部失败导致用户失去信任 | 展示进度、部分成功结果、失败原因和单项重试 |
| 范围风险 | 过早增加集成、协作和实时能力，无法验证核心价值 | 坚守单文件上传到决策支持的 P0 闭环 |
